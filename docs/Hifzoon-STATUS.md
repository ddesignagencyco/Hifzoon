## Part 1 — What is done

### 1.1 Platform (PLAT) ✅

| Area         | Implementation                                                                                                                                 |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Config       | `env.schema.ts` validates every variable with zod at boot. The process **refuses to start** on bad config rather than failing at request time. |
| Envelope     | `ResponseInterceptor` wraps every success in `{ data, meta }`; `AllExceptionsFilter` gives one error shape API-wide.                           |
| Guards       | JWT, roles, consent and throttling registered once in `app.module.ts` as global providers.                                                     |
| Request IDs  | Middleware stamps every request; returned in `meta.requestId` and written into error bodies and audit rows.                                    |
| OpenAPI      | Swagger at `/api/docs`; the served spec and the committed artifact are generated by the same builder so they cannot drift.                     |
| Health       | `/health/live` (process only) and `/health/ready` (checks DB + Redis with latency).                                                            |
| Storage      | Real S3 client behind a service, with signed URLs.                                                                                             |
| Integrations | Six provider interfaces (video, payment, mailer, messenger, Quran content, speech) with **fake/log adapters**.                                 |
| Audit        | Append-only audit trail enforced by a database trigger.                                                                                        |
| Settings     | 25-key typed settings registry, read in one query overlaid on defaults.                                                                        |

### 1.2 Accounts, consent and families (AUTH) ✅

- Email/password auth with **Argon2id** hashing, plus Google/Apple OAuth env placeholders (see §4).
- Access token 15 min; **refresh token rotation with reuse detection** — replaying a revoked token revokes the entire session as suspected theft.
- Refresh TTL is role-dependent: staff 12 h, personal accounts 30 days.
- Account lockout after 10 failed attempts, which also revokes all sessions and queues an email.
- **Timing-attack mitigation** — a dummy hash is verified when the account does not exist, so response time does not leak account existence.
- TOTP 2FA (staff only) with the secret AES-encrypted at rest and 8 single-use recovery codes.
- Consent is modelled **per purpose, independently** — `AI_TRAINING` can be withheld while delivery consent is granted.
- Withdrawal never deletes: it flips status, appends an immutable event, and runs consequences (recording flags cleared, audio keys nulled and queued for deletion).
- A child is a `student` row with **no email and no account** — data minimisation by design (CR-04).
- Guardian verification by emailed 6-digit code with timing-safe comparison; under-13s are blocked until a guardian is verified (CR-10).

### 1.3 Scheduling, matching and admission (SCH, ADM) ✅

- Partial **RFC 5545 RRULE** parser — supports `FREQ=DAILY|WEEKLY`, `INTERVAL`, `BYDAY`, `UNTIL`, `COUNT`, and **rejects anything else at write time** rather than mis-expanding it.
- **DST correctness is a headline feature.** A recurring class keeps its local wall-clock time, so its UTC instant shifts by an hour across a transition. Detection works by _round-tripping_ the UTC instant back to a wall clock rather than comparing offsets, and a nightly job flags clashes before they happen.
- Slot search walks a 15-minute grid in the **teacher's** zone over a 62-day horizon, drops slots under 2 h away and any that overlap an existing session, then renders in the **visitor's** zone.
- Teacher suggestions are transparent and explainable — language is a hard filter, then +25 subject, +10 age group, +5 gender, +rating.
- Trial booking creates session + enrolment + link in one transaction, with a 24 h no-show follow-up task.
- **One live enrolment per student per course** — prevents double billing and split lesson history.
- Double booking is prevented by a PostgreSQL GiST exclusion constraint, not just application logic.

### 1.4 Classroom and Mushaf (CLS) ✅

- Socket.IO namespace `/classroom` with room-token HMAC verification that needs **no database hit**.
- Early-join window enforced on both sides of the session; cancelled sessions refused.
- Attendance is **segment-banked** — rejoining adds elapsed minutes, and a nightly sweep closes anyone left open.
- Mushaf page and highlight sync broadcast from the server (never relayed by a client), with draw/Tajweed overlays that are ephemeral by design.
- **Recording requires consent from every enrolled student** — one missing child blocks the whole recording, and the error names who is missing (CR-02). Records are auto-deleted after 90 days.
- Bandwidth advice degrades **video before audio or Mushaf sync** are ever sacrificed.
- Mushaf text comes only from the licensed provider, with a cache TTL set one day under the 7-day licence ceiling. Unlicensed, it returns `501` in production and structural data in development.

### 1.5 Lesson records and QA (REC, QA) ✅

- Mistakes carry exact position — surah, ayah, word index, type, optional Tajweed rule.
- **Dismiss is not delete.** A dismissed mistake stays as a row so the AI false-positive rate remains measurable.
- Lesson cards support prefill from the class, a **48-hour edit lock**, and an append-only edit log written in the same transaction as the change. Post-lock edits require a reason and are supervisor-only.
- AI summaries are **approved, not merely submitted**, before a family can see them (FR-REC-05).
- QA ratings, weighted rubrics with mandatory per-criterion scoring, monthly random sampling, and scorecards with automatic `flag = mean < 3`.
- Safeguarding cases carry an SLA, and `alertedAt` is stamped once and never reset, so reopening a case cannot buy extra time.

### 1.6 Billing, CRM and admin (BIL, OPS) ✅

- Money is handled in **integer minor units only** — no floats anywhere in billing.
- Non-sequential invoice numbers; discounts rejected rather than clamped.
- Payment webhooks are **idempotent** via a unique provider ID; an invoice is only `PAID` when successful payments sum to the total.
- **Dunning ladder** at 1/3/7 days, then cancellation, with per-invoice error isolation so one bad invoice cannot abort the sweep.
- Payroll computes one transaction per teacher, never recomputes an existing entry, and turns `NO_SHOW_TEHER` into a negative deduction line.
- CRM lead flow is monotonic — `WON`/`LOST` are immutable, `LOST` requires a reason.
- Admin console provides cross-entity search and teacher provisioning that **never** grants matchability.

### 1.7 Notifications and workers (NTF) ✅

- Quiet hours honoured per locale with midnight wraparound; only genuinely safety-critical alerts bypass them.
- A notification row is written **before** the send is attempted, so a delivery failure is visible rather than silent.
- Email bodies are HTML-escaped; sends are idempotent by notification ID.
- Two reminders per class (24 h and 15 min before), re-checked and cancelled on reschedule.

### 1.8 Background worker ✅

BullMQ processors for: session materialisation, DST clash detection, reminder planning, class closing,
recording lifecycle (with **monotonic** status so out-of-order webhooks are ignored), data requests, lesson
cards, billing retries and retention.

## Part 2 — The main logic: how we handle things

This is the reasoning that shapes the system. Ten decisions explain most of the code.

### 2.1 Cross-cutting concerns live in exactly one place

Guards, the response envelope, the error shape, rate limiting and request IDs are registered as **global
providers** in `app.module.ts`, not per module. A new feature folder inherits authentication, envelope
shaping, throttling and audit for free — the only way to add a feature is to make a folder, and it cannot
accidentally ship unauthenticated.

### 2.2 Authorisation is split by concern, on purpose

| Layer           | Answers                                      | Mechanism                                    |
| --------------- | -------------------------------------------- | -------------------------------------------- |
| `JwtAuthGuard`  | _Who_ is calling? Is the session still live? | Global; re-reads user + session each request |
| `RolesGuard`    | _What kind_ of user is this?                 | `@Roles()` metadata only                     |
| `PolicyService` | _Does this_ user own _this_ resource?        | Ownership/tenancy                            |
| `ConsentGuard`  | May this action proceed for this child?      | `@RequiresConsent()`                         |

`RolesGuard` explicitly refuses to do ownership checks. Mixing "is staff?" with "is this _your_ child?"
is how IDOR bugs get written, so the two are separate mechanisms with separate names.

### 2.3 Revocation beats token cleverness

The JWT is deliberately thin (`sub`, `roles`, `staff`, `sid`). The strategy **re-reads the user and session
on every request**, trading one indexed lookup for the ability to revoke a session instantly. Locking an
account or revoking a refresh token takes effect on the very next call rather than whenever the token
happens to expire.

### 2.4 Time is stored in UTC and chosen in local

The rule is: **store UTC, decide in local, render in the viewer's zone.** A parent in Lahore and a teacher
in Dubai both see 19:00 local for the same instant. Recurrence expands in the _family's_ zone from the
start, never by iterating UTC and converting — the DST service exists because that distinction is the whole
problem.

### 2.5 Invariants that must never break live in the database

Application logic can be bypassed by a migration, a script or a future service. Five invariant triggers and
seven helper functions enforce the rules that matter most:

| Trigger                                 | Enforces                                       |
| --------------------------------------- | ---------------------------------------------- |
| `audit_log_append_only`                 | Audit rows cannot be updated or deleted        |
| `lesson_card_lock_guard`                | The 48-hour lesson-card lock, server-side      |
| `teacher_profile_ready_to_match_guard`  | Matchability needs its inputs                  |
| `teacher_profile_readiness_consistency` | `readyToMatch` is derived, not set arbitrarily |
| `assessment_examiner_independent`       | An examiner cannot assess their own relative   |

The `recompute_teacher_readiness()` function is called **before** flipping status, because ordering against
the trigger is load-bearing. A sixth trigger, `set_updated_at`, is applied generically across every table
that carries an `updated_at` column.

### 2.6 Async where it must be, never inline

Emails, exports, video and AI never run inside a request. Jobs go to BullMQ, and every processor is written
to be **idempotent** — because BullMQ retries. This is why `materialisedUntil`, `alertedAt` and
`idempotencyKey` fields exist: they make a second execution harmless.

### 2.7 Consent withdrawal has consequences, not just a flag

Withdrawing `CLASS_RECORDING` does not merely flip a column — it clears Tajweed data on scheduled sessions
and queues deletion of the recordings. Withdrawing `AI_VOICE` nulls the audio keys and schedules purge.
Consent that is only recorded and never enforced is worse than none, because it creates false assurance.

### 2.8 Fail loudly in production, quietly in development

- A fake provider throws `501 NOT_IMPLEMENTED` with the missing env var names. Recording a class without a
  real video provider would otherwise _appear_ to work — the dangerous failure mode.
- Placeholder secrets are **rejected** in production, as is `CORS_ORIGINS=*`.
- Dev never leaks: `forgot-password` always returns success so accounts cannot be enumerated, and a dummy
  hash keeps login timing constant.

### 2.9 Audit never breaks the request

`AuditService.record` **never throws**. It increments a failure counter and logs at error level, surfacing
`failedWrites` in the audit listing. An audit outage degrades observability; it must not take down booking
or payment.

### 2.10 One rule per module folder, services do the work

Controllers are thin: validate, delegate, let the global envelope and filter shape the reply. Business
logic lives in services. Interceptors record audit using the **handler's return value** rather than
re-reading, so what is logged is what was actually sent to the client.

## Part 3 — How it is wired

```
Browser (not built yet)
   │  REST /api/v1        WebSocket /classroom      WebRTC
   ▼                      ▼                          ▼
┌──────────────────────────────────────────────────────────────────┐
│  NestJS API  (global: JWT → roles → consent → throttle)           │
│  ┌──────────┬──────────┬──────────┬──────────┬──────────────────┐  │
│  │  auth    │ consent  │ families │ courses  │ …17 modules…    │  │
│  └──────────┴──────────┴──────────┴──────────┴──────────────────┘  │
└───────┬──────────────────────┬─────────────────────┬──────────────┘
        ▼                      ▼                     ▼
   PostgreSQL 16          Redis + BullMQ          S3 / MinIO
   95 models, 5 triggers  cache, queues,          recordings,
   GiST no-overlap        Socket.IO adapter       documents
        │
        └──▶ Worker process (same image, `node dist/worker.js`)
```

The API is **stateless**; the worker is the **same Docker image with a different entry point**, so a slow
job can never block a request.

### 4.3 Open product decisions (block real adapters)

These are recorded in TRD section 21 and the tracker. They are **business decisions, not engineering
ones** — no amount of code resolves them:

1. **Payment provider and operating country** — Stripe does not serve Pakistan-registered companies.
2. **Quran licence** — determines whether Mushaf text may be cached at all.
3. **Video provider** — LiveKit vs alternative.
4. **Safeguarding lead** — must be named before QA escalations can go anywhere.
5. **Product naming** — "Hifzoon" vs "Qirva" in the SRS diagrams.
